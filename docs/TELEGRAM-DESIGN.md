## 一、为什么要单独写这份

项目从 v1 的"备忘录一天一页"切到 v4 的"Telegram 单一入口"时，Telegram 只被当成
**收发管道**用：收一句、回一句。于是这一层的设计基本没做，问题都堆在别处爆发。

实测出来的账（2026-10-03 一天 4 次真实交互，**3 次出问题**）：

| 交互 | 你发的 | 系统做的 | 性质 |
|---|---|---|---|
| 1 | 一段关于"学原理"的感慨 | 判成待办，写进提醒事项 | 分类判据错 |
| 2 | `改为备忘录` | **新建**一条叫「改为备忘录」的备忘 | 把"操作"当成"内容" |
| 3 | `上午九点`（回答追问） | **新建**一条标题是「上午九点」的日程 | 把"补全"当成"新内容" |

三次里**两次是同一个根因**：系统只认「这一句是新内容」，不认「这一句是对上一条的操作」。

**一次修一处形态是打补丁**（已经打过一次：给"补时间"加了单一槽位与合并逻辑），
根因仍然在。这份文档的目的是在动手前把这一层想清楚。

## 二、Telegram 的 API 面（实测 + 权威文档，2026-10-03 核对）

### 2.1 现状：只用了 5 个方法

```
getMe · getUpdates · sendMessage · editMessageText · answerCallbackQuery
```

`src/telegram.py` 已有 **541 行**，其中相当一部分在处理"跨消息的状态"：
offset 推进、callback 的 `callback_data` 编码、pending 槽位、TTL、
过期回调清理、以及 `--drain` 这类历史消费逻辑。

### 2.2 完全没用到的原生能力

| 机制 | 现状 | 对本项目的价值 |
|---|---|---|
| **`reply_to_message`（原生回复）** | ❌ 未用 | ★★★ **天然精确指代**，见 §4 |
| `setMyCommands`（命令菜单） | ❌ 未用 | ★★ 符号词表的原生展示位，见 §5 |
| `ReplyKeyboardMarkup`（底部键盘） | ❌ 未用 | ★ 符号可以作为按钮常驻，见 §5 |
| `MessageEntity` 类型化解析 | ❌ 未用 | ★ hashtag / bot_command / date_time 是**服务端判断**的 |
| `force_reply` | ❌ 未用 | ☆ 新 API（10.3），可强制你回复某条 |
| `deleteMessage` | ❌ 未用 | ✗ **刻意不用**：架构规定 agent 不删任何东西 |
| Webhook 模式 | ❌ 未用 | ✗ 需要公网可达入口，Mac mini 没有 |
| Inline mode / Mini App | ❌ 未用 | ☆ 见 §6 的取舍 |

### 2.3 三个必须记住的硬约束

**① `callback_data` 上限 64 字节。**
所以按钮里**放不下正文**，只能放"选择 + 一个标识"。这不是实现细节，是设计约束：
凡是按钮携带的信息，都必须是**短标识**，正文必须另行可取。
（v1 实测过 65 字节 → API 直接报错。）

**② 回复一条**已被删除**的消息会让整条发送失败。**
`ReplyParameters.message_id` 文档原文：需要 `allow_sending_without_reply=True`
才会"目标消息找不到也照发"，否则请求直接失败。所以用原生回复时必须带这个开关，
否则"我的回执被删了 → 你的回执也发不出去"会连坐。

**③ `getUpdates` 与 webhook 互斥，且更新只留 24 小时。**
守护挂超过 24 小时，期间的更新就永久丢了（不是延迟，是丢）。
这跟"守护必须常驻"是同一个约束的两面。

### 2.4 一个容易忽略的事实：`reply_to_message` 是**完整对象**

回复某条消息时，Telegram 给的 `reply_to_message` 是**整个 Message 对象**，
里面就有 `message_id` 和 `text`。

也就是说：**"你回复的是哪条消息" + "那条消息的原文"，都是 Telegram 免费给的**，
不需要我们记、不需要我们猜。这一条直接决定了 §4 的设计方向。

## 三、这一层真正的矛盾：架构要求无状态，Telegram 到处是状态

`ARCHITECTURE.md` 的核心是：

> **agent 无状态，journal 是传感器** —— "不构成闭环 → 不会左脚踩右脚"

但 Telegram 这一层**处处是状态**。2026-10-03 的裁决（见 [`SYMBOL-SCHEME.md`](SYMBOL-SCHEME.md) §4.6）
把方案 2 落地后要保留的状态**从四种减到两种**：

| 状态 | 为什么需要 | 失效表现 | 现状 → 裁决后 |
|---|---|---|---|
| **offset**（读取位置） | 不持久 → 重启后重复消费 | 同一条被记两遍 | ✅ 已落盘 → **保留**（通道机制，与业务无关）|
| **消息可编辑性** | 回执若需反映最新状态 | 重绘失败/内容未变报错 | ⚠️ 有 `NOT_MODIFIED` 补丁 → **视回执形态而定**（§5.1）|
| ~~`callback_data`~~（按钮指向哪条） | 按钮要标明"我是给哪条的" | 对不上号 → 点了没反应 | ❌ **删掉**：不再有"选一个"按钮 |
| ~~`pending`~~（等用户补充什么） | 一问一答要有"上文" | 被清掉/接错条 | ❌ **删掉**：不再追问，缺什么带符号重说 |

> 划掉的两项正是今天两次故障的所在地（槽位被清、按钮绑错消息号）。
> **它们不是"被修好了"，是"被删掉了"** —— 这是方案 2 最实在的收益。

**结论：状态不可避免，能做的是"把状态放哪"。** 三条路线：

| 路线 | 做法 | 代价 |
|---|---|---|
| A. 全部自建 | 状态存本地文件（= 旧现状） | 状态一多就开始互相打架 |
| B. 全部交给 Telegram | 用原生回复、原生实体、服务端判断 | 受 API 约束，能力有上限 |
| C. **只留通道必需的那一个（offset）** | 业务状态一个都不留 | 代价是放弃"引用/追问"这类交互 —— **已裁决接受** |

**结论是 C，但比原方案更彻底**：

~~引用交给 Telegram，其余自建~~ → **引用也不做**。

理由：2026-10-03 裁决时逐条对过 `ARCHITECTURE.md` §十一 的判据，
「原生回复作引用」命中判据 1、3（要跨交互记住"那条回执对应哪条事"）——
**它省下的只是"重打一遍标题"的几秒钟，代价是重建一整套 pending 状态。**
不划算。

## 四、方案 2 落地后，Telegram 层的唯一职责

符号声明方案（见 [`SYMBOL-SCHEME.md`](SYMBOL-SCHEME.md)）把**分类判断**从系统移回给你。
于是 Telegram 这一层的职责被削到很薄：

```
你发的消息  →  ① 认出行首符号  →  ② 剥掉符号  →  ③ 按符号写对应 App
                                    ↓
                              ④ 回执（可选）
```

**关键：这一层不再需要"理解"任何东西。** 它不判断语义、不需要上文、不需要追问。

这样一来，§3 表里的四种状态有两种**直接消失**：

| 状态 | 方案 2 之后 |
|---|---|
| `callback_data`（按钮指向） | ❌ 不需要（没有"选一个"了）|
| `pending`（等补充） | ❌ 不需要（缺什么由你自己再说一句，带符号即可）|
| offset | ✅ 仍需要（这是通道机制，与业务无关）|
| 消息可编辑性 | ⭕ 仅在"回执是否需要更新"时涉及 |

**这是本文最重要的一个推论**：把判断权交回给你之后，Telegram 层从
"一个有状态的对话机"退回成"一条记录管道" —— 而后者正是这个项目擅长的形态。

## 五、设计点（2026-10-03 已逐条裁决）

> 本节原本是"待你定"的清单。三项已裁决，两项仍是倾向、待实施时确认。

### 5.1 回执要不要发？ → **倾向：发，极简**

| | 发 | 不发 |
|---|---|---|
| 体验 | 每条都有确认，心里有底 | 安静，像发给自己 |
| 代价 | 消息条数翻倍，聊天记录半屏是回执 | 打错符号时你**不知道** |
| 与"符号声明"的关系 | 符号打错了能立刻看见 | 错了只能去 App 里发现 |

**倾向：发，但极简**（一行，如 `✓ 待办：交电费`）。理由是符号方案的错误
是**你造成的**，而"看得见"是这个方案唯一的安全网。

⚠️ 若最终决定**不发**，则 `SYMBOL-SCHEME.md` §6 里那条
"回执如实显示去向"的缓解措施不成立，需一并改掉。

### 5.2 系统还能不能"提问"？ → **已裁决：只报错，不提问，不写入**

| 情况 | 系统的反应 | 性质 |
|---|---|---|
| `@` 后面没有可解析的时间 | **报错并拒绝写入** | 陈述事实 |
| 写入失败（权限/超时） | 报错并给出退路 | 陈述事实 |
| （曾经的候选）`@` 缺时间 → 退回当备忘写 | ❌ **不做** | 猜 |
| （曾经的候选）`@` 缺时间 → 追问"什么时候？" | ❌ **不做** | 要求你再交互一次 |

**报错 vs 提问的区别是关键**：报错是**陈述事实**（我做不到，原因是什么），
提问是**要求你补全**（你得再交互一次）。后者引入跨消息状态，前者不引入。

`@` 缺时间的完整处置见 [`SYMBOL-SCHEME.md`](SYMBOL-SCHEME.md) §5.3。

### 5.3 用不用原生回复来"引用上一条"？ → **已裁决：不做**

`reply_to_message` 确实免费携带 `message_id` 与 `text`（§2.4 已确认），
技术上是个**零猜测**的引用方式。但逐条对 `ARCHITECTURE.md` §十一 的判据：

| 判据 | 是否命中 |
|---|---|
| ✗ 需要跨两次交互记住东西 | **命中** —— 要记住"那条回执对应哪条待补全的日程" |
| ✗ 需要超时 / 重入 / 确认屏 | **命中** —— 回执可能被删、可能过期 |

**省下的只是"重打一遍标题"的几秒钟，代价是重建一整套 pending 状态。**

**裁决：不做。** 缺信息就带符号重发一条完整的。
这条同时把 §3 的两类状态永久删掉（详见 [`SYMBOL-SCHEME.md`](SYMBOL-SCHEME.md) §4.6）。

### 5.4 bot 命令菜单（`setMyCommands`） → **倾向：只设 `/help`**

Telegram 在私聊里会在你打 `/` 时**自动补全命令**。这是唯一一个"符号词表的原生展示位"。

约束（文档确认）：命令名只能 `[a-z0-9_]`，**`@` 和 `#` 不能做命令名**。

| 选项 | 说明 |
|---|---|
| 设一组命令（如 `/memo` `/event`） | 有发现性、可补全；但**要维护两套词汇**（符号 + 命令），与"不要混"冲突 |
| **只设 `/help`**（倾向） | 一套词汇（符号）；`/help` 是唯一入口，内容就是符号表 |

### 5.5 底部常驻键盘（`ReplyKeyboardMarkup`）？ → **不可行，已排除**

Telegram 的底部键盘按钮是**"发送内容"，不是"插入字符"** ——
点了就把按钮文字当消息发出去，没法"先点符号再打字"。

所以这条路**做不到"先给个符号"**。记录在此以免以后再想一遍。

### 5.6 长轮询 25 秒的延迟 → **倾向：保持，但回执先发**

现在是 25 秒长轮询。你发一句到系统开始处理，**最坏等 25 秒**。

| 选项 | 代价 |
|---|---|
| 缩短到 5 秒 | 请求数 ×5，日志变吵 |
| **保持 25 秒**（倾向） | 偶尔感觉"没反应"（实测你今天就以为它死了）|
| 改用 webhook | 需要公网入口，Mac mini 没有（且 README 明确不建议映射公网）|

**缓解办法不是缩短轮询，而是"先回执再干活"**：收到就发一行"收到"，
写完 App 再补结果。代价是消息更多 —— 与 §5.1 的结论相关联，
**若 §5.1 决定不发回执，这条也要重新考虑**。

## 六、明确不做的（免得以后反复讨论）

| 不做 | 理由 |
|---|---|
| Webhook | 需要公网可达；本项目明确"不要把端口映射到公网"（见 README 安全设计）|
| Mini App / Web App 表单 | 那是方案 3（表单化），已定不走 |
| Inline keyboard 追问 | 那是方案 1（按钮问），已定不走 |
| Inline mode（`@bot xxx` 在别处调用） | 与"专用 bot、单一入口"的定位不符 |
| `deleteMessage` | 架构规定 agent 不删任何东西，包括自己发的 |
