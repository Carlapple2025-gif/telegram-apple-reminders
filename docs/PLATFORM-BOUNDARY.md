# 平台边界与版本策略（提案 · 未裁决）

> **性质：提案。** [`ARCHITECTURE.md`](ARCHITECTURE.md) 仍是设计权威。
>
> **2026-10-05 进展**：第 0、1 步**已执行** —— 契约已写下来并**生效**
> （[`KERNEL-CONTRACT.md`](KERNEL-CONTRACT.md) + [`../VERSION`](../VERSION) = `1.0.0`，
> 边界与版本由自检断言守着）。**§六 的第 2–8 步仍未裁决**：
> 本文其余部分（注册表怎么切、按什么顺序切）仍是待讨论的方案，不是已定的做法。
>
> **起因**（2026-10-05 审查）：目标是把稳定的"平台"与可插拔的"功能"分开，
> 让加功能时**不触碰底层架构代码**，并用三位数版本号
> （第一位大版本 / 第二位功能 / 第三位热修）表达每次改动的性质。

## 〇、先说三句结论

| # | 结论 |
|---|---|
| 1 | **三位数的形状是对的** —— 它就是语义化版本 `MAJOR.MINOR.PATCH`。但它是**结果**，不是**机制**：先有"公开契约"，才谈得上"什么算破坏兼容"。 |
| 2 | **这个项目已经八成是平台了。** 缺的不是插件框架，是**把四处硬编码的 if 链收成一张注册表**。 |
| 3 | 真正让改动不碰底层的，是**一份写下来的契约 + 一条自检断言**。这个机制本项目**已经有了**（见 §二.5），把它扩一格即可，不必新造。 |

反过来说也成立：**光有三位数版本号，一行底层代码都不会少碰。**
编号是契约的影子；没有契约，影子只能凭感觉画 ——
而凭感觉画，就是现在 CHANGELOG 里那套 `v1.0 / v1.1 / v4.0 / v4.1`。

## 四、建议的边界

### 4.1 内核（冻结；改它需要一次架构裁决）

规则三条，都已**变成可执行断言**（`VERSION` = `1.0.0` 起，见 `docs/KERNEL-CONTRACT.md`）：

1. **内核模块不得 import 功能模块**。
2. **功能模块不得 import 另一个功能模块**。
3. **`kinds.Item` 是内核 ABI**：字段只能加、不能改语义、不能删（删要走 MAJOR）。

规则 1、2 落地时**不是从零开始**：现状已有 4 条越界边（§1.1 的表）。
断言的做法是**白名单 + 只许缩小** —— 每条越界边在代码里登记理由与消除时机，
**新增的第 5 条越界边会立刻让自检变红**。这比"假装现在很干净"有用得多。

### 4.2 功能（每个自包含，靠一张表登记）

```python
# features/__init__.py —— 全项目唯一"知道所有功能"的地方
Feature(
    name="todo",
    version="1.0.0",                 # 功能自己的版本（第二位数字在这里才有含义）
    requires_core=">=1.0,<2",        # 兼容声明（照 VS Code 的 engines 字段）
    symbols=("", "-", "*"),          # 行首声明 → 由路由统一匹配
    parse=..., sink=...,             # 现 routes/intake 里的对应逻辑搬进来
    journal_events=("todo_added",),
    reply=Reply(label="待办", place="提醒事项"),
    digest_sections=(...),           # 日报区块（可为空）
    reads=(...),                     # 只读能力，供日报与命令共用
)
```

判据：**加第 4 种 kind 只应碰两个地方** —— 新增的功能模块 + 注册表一行。
若还需要改 `routes` / `intake` / `report` / `daemon`，说明边界漏了。

### 4.3 准入门槛（平台真正该提供的东西）

[`ARCHITECTURE.md`](ARCHITECTURE.md) §十一 的**七条判据就是插件准入条件**：

```
✗ 需要跨两次交互记住东西      ✗ 需要重绘整条消息来体现进度
✗ 需要超时 / 重入 / 确认屏      ✗ 需要猜"这条是不是同一件事"
✗ 让 agent 拥有"删"权限         ✗ agent 用自己写的东西作为下次写入的依据
✗ agent 在"要动你的数据"时不先回显确认
```

平台化之后要把这七条**变成可执行的断言**（而不是文档里的一段话）：
插件模块内不得出现 `delete`；插件不得声明跨消息状态字段；
插件不得 import 另一个插件。**否则插件化会成为绕开架构约束的捷径。**

### 4.4 平台化会打破的既有约束（诚实清单）

这张表是这份提案里最该先看的部分 —— 因为**每一条都是现在靠"硬编码 + 断言"守住的东西**，
改成注册表时它们会一起松动：

| # | 会被打破的约束 | 为什么 | 守护点（现状） |
|---|---|---|---|
| 1 | **agent 只增不删** | 注册表天然需要"启用/禁用"，一旦引入 `unregister`，删除语义就回来了 | `selftest.py:1195-1200`（memo/applecal 无 `delete()`）+ `:1204-1214`（v4 路径不得调 `rem.delete`）—— ⚠️ **这两条是硬编码模块名，不是通用规则**，加插件必须同步扩 |
| 2 | **agent 无状态、不构成闭环** | 插件很容易自带状态（记账余额、周报计数缓存），那就是 journal 之外的第二份状态 | **目前没有任何自动断言**，只有 `journal.py:5-37` 的文档。这是最大的一条裸露面 |
| 3 | **一处实现** | 每个插件自带一份符号表/事件名表，正是插件化最容易长出来的形态 | 而 `routes.py:59 ↔ parse.py:55`、`journal.py:108-116 ↔ intake.py:82-89` **已经是两处既成事实** |
| 4 | **读不到 ≠ 没有 / 不静默失败** | `report.py:172` 用 `"提醒事项" in e` **字符串匹配**反查错误来源；品类可插拔后前缀由插件生成，内核保证不了词形 → 判据**静默失效** | `report.py:172-175`、`commands.py:119,149-153,171-177` |
| 5 | **日报四段固定** | 区块可插拔后，现在"逐段断言文案"的写法全部失效 | `selftest.py:2643-2661`（断"✅ 今日完成 1 件"这类字面量）→ 必须改成**断言区块协议** |
| 6 | **看门狗不加状态文件** | 多个定时产物（周报/日报）共享一个 watchdog 时，按日期粒度的冷却不够用 | `watchdog.py:64`（`_ALERTED_IN_PROCESS` 按日期去重）、`:84-88` —— 加任务就必须加维度 |

**结论**：平台化不是"把 if 换成表"这么轻。它**同时**是一次约束防线的重建 ——
第 1、2、4 条必须在动手之前先想清楚，否则会得到"能插拔、但架构约束守不住"的系统，
那比现在更糟。

## 五、版本策略

### 5.1 三位数的含义要按"兼容性"定，而不是按"大小"定

语义化版本（[SemVer 2.0.0](https://semver.org/)）的定义是：
**MAJOR = 不兼容的变更；MINOR = 向后兼容地新增功能；PATCH = 向后兼容地修 bug。**
与"第一位大版本 / 第二位功能 / 第三位热修"**形状一致**，所以构思是对的。
差别在于**每次加一时依据什么**：

| 位 | 什么时候 +1（任一条命中就进这一位） |
|---|---|
| **第 1 位** | ① 输入语言变了（符号表增/删/改语义）② **同一条输入落点变了**（写进哪个 App / 记哪个 journal 事件）③ journal 或 config 需要数据迁移 ④ 功能契约不兼容 |
| **第 2 位** | 新增功能，且上面四条**一条都不命中** |
| **第 3 位** | 修 bug，完全不改契约 |

第 ① 条很硬：**"忘了打符号就进待办"这种默认行为的改变，也进第 1 位** ——
因为使用者（你）必须重新学一遍。单人项目里，**第一位唯一真实的含义
就是"我要不要重学"**。

### 5.2 规范里的几条硬规矩（最容易踩）

| 规矩 | 依据 |
|---|---|
| 不许前导零（`1.02.3` 非法） | SemVer 规则 2 |
| 每位**各自**数值递增：`1.9.0 → 1.10.0`，不是 `2.0.0` | 规则 2 |
| **发布过的版本内容不得再改**，只能发新版本 | 规则 3 |
| `0.y.z` 是初始开发期，任何东西都可变；`1.0.0` 的定义是"公开 API 定下来了" | 规则 4、5 |
| 进第 1 位时，第 2、3 位**归零** | 规则 8 |
| 预发布用 `-rc.1`；构建元数据用 `+20261005` | 规则 9、10 |
| `v1.2.3` **不是**版本号，是 tag 名（版本号是 `1.2.3`） | 官方 FAQ |

### 5.3 平台 + 功能 = 两条轴（这是三位数单独表达不了的）

标准做法是**版本 + 兼容声明**，参照
[VS Code 扩展 manifest](https://code.visualstudio.com/api/references/extension-manifest)：
`version` 是 SemVer，同时必须有 `engines.vscode` 声明兼容的宿主版本范围，
且**不允许写 `*`**（"Cannot be `*`"）。Home Assistant 的集成 manifest 同理。

对应到本项目：

| 轴 | 放在哪 | 例子 |
|---|---|---|
| 内核版本 | `VERSION` 文件（**单一来源**） | `1.2.0` |
| 功能版本 | 注册表条目里的 `version` | `todo 1.0.0` / `ledger 0.3.1` |
| 兼容声明 | 注册表条目里的 `requires_core` | `>=1.0,<2` |

**单一来源 + 一致性断言**：版本号写在三个地方就一定有两处是错的。
`VERSION` 是唯一来源，CHANGELOG 顶部引它，自检断言两者一致 ——
这完全是本项目已有的自检风格（严格 `plistlib` 解析、接口清单断言）。

### 5.4 现有编号与这套规则冲突的一处（必须裁决）

`v4.1`（2026-10-03）**删掉了自然语言分类**（`classify.py` 405 行），
把输入从"说什么都行"改成"必须打符号" ——
使用者必须重学怎么用。**按 5.1 的规则，这是第 1 位的变更，不是第二位。**

所以两条路只能选一条：

| 选 | 含义 | 后果 |
|---|---|---|
| **A. 第一位 = 架构里程碑**（现状） | 与兼容性无关 | 三位数**表达不了**改动性质，那就不该假装它能 —— 继续用"代号 + 日期" |
| **B. 第一位 = 破坏兼容**（建议） | 每次第一位 +1 都要能说清"你要重学什么" | 需要一次**冻结与改名**（见下），此后数字才有信息量 |

**建议 B**，并在冻结时做一次映射，让历史编号留在 CHANGELOG 里当代号：

```
v1.0 / v1.1            → 史前（备忘录那套）
v4.0 架构推翻           → core 1.0.0 的"前身"，记作 pre-1.0
v4.1 符号声明（破坏性）  → **core 1.0.0 从这一刻算起**（公开 API 定稿）
之后的平台化改造         → core 1.1.0（不动契约）
```

理由正是 SemVer 规则 5：**`1.0.0` 的定义就是"公开 API 定下来了"。**
而 [`ARCHITECTURE.md`](ARCHITECTURE.md) 头部写的是"定稿于 2026-10-03"——
两者是同一件事，只是当时还没有"公开 API"这个概念。

### 5.5 还有一样东西必须版本化

**journal 的事件 schema。** 这是本系统里**唯一真正需要向后兼容**的东西：
Apple 应用会变、代码会变、机器会换，而已写下的 `.jsonl` **永不修改、丢了不可再生**
（`journal.py` 的架构约束）。所以：

- 事件名与字段集要有一份声明（现在散在 `journal.py:108-116` 的 `EV_*` 常量里）；
- 加字段 = MINOR；改字段语义 / 删字段 = MAJOR；
- 这条**比代码版本更重要**，因为代码可以回滚，已写入的读数不能。

**这条不是假想需求 —— 它已经发生过一次了。** 2026-10-05 的提交 `a1e4733`
（"journal 记下日程的重复规则"）给 `event_added` 事件**加了字段**，
而单据 `append(event, **fields)`（`journal.py:135-161`）对任何字段都不校验、
不报错、不留痕。也就是说：**上一版代码读今天的 journal，与今天的代码读上个月的 journal，
都只能靠约定**。这正是需要"数据轴版本"的地方。

### 5.6 关于"两条版本轴 + engines 式兼容声明"：**不建议照搬**（这是提案与 VS Code 的关键分歧）

VS Code 那条"`engines.vscode` 必填、且**不允许写 `*`**"的规矩，
解决的是**宿主与插件由不同的人、在不同的时间、独立发版**的问题 ——
5 万个第三方扩展、几十个宿主版本、一个跨版本兼容矩阵。
它的价值在于**约束第三方**。

本项目的插件与宿主**同仓、同一次提交、同一个使用者**。
于是 `requires_core` 的值永远等于"当前 core 版本" ——
它是一个**恒真断言**，写它等于写 `assert True`。所以：

| 提案 | 判断 | 理由 |
|---|---|---|
| git tag | ✅ **要**，立刻 | 零成本、立刻可用；这是"回滚锚点"这一条真实价值的兑现 |
| `VERSION` 文件 | ✅ **要**，立刻 | 但含义是**契约版本**，不是产品版本；单一来源 + 断言，见 §六 第 1 步 |
| 插件契约 | ⚠️ **要，但只写"登记表 + 断言"，不写 Protocol** | 现在**只有一个插件**（watchdog）。为一个实例写接口协议是拿假想需求换复杂度；等 P1 周报（第二个插件）落地时再抽 |
| 每条功能一个版本号 | ❌ **不要** | 同上：只有一个使用者、功能不单独发版，功能版本号没有读者 |
| engines 式 `requires_core` 声明 | ❌ **不要**（现在） | 恒真断言。**触发条件**：出现"第二个使用者 / 第二台机器 / 功能单独发版"任一条时引入 |
| **journal schema 版本** | ✅ **要** | 这才是本项目真正意义上的"第二条轴" —— **代码轴 + 数据轴**。数据跨时间，代码不跨 |

**一句话**：本项目需要的不是"两条代码版本轴"，而是"**一条代码轴 + 一条数据轴**"。

## 六、落地顺序

**按"下一批功能落在哪里"排序，不按"看起来是否优雅"。**

依据：README §八 的下一步是 **P1 周报 / P2 守护可观测性 / P3 智能体诊断**。
这三件事**都不是新的 kind** —— 它们是"日报新区块 / 新命令 / 新通道"。
所以最高价值的接缝是 C → E → D，**kind 注册表反而排最后**。

### 6.1 接缝的验收结果（2026-10-05，用 P1 周报检验）

当初做第 2、3 步时说好：**用周报当第一个真实用例，看接缝是不是真的够用**。
结论是**一半对**，如实记下：

| 我说过的 | 实际 | 判定 |
|---|---|---|
| 周报 = 同一份数据、不同的区块选择 | **渲染这一半完全成立**：加了 6 个 `digests=("weekly",)` 的区块，`build_report` **一行没改** | ✅ |
| 投递链可以共用 | 抽出了 `_deliver`（存档/推送/心跳/留痕），日报周报共用 —— 但这是**新写**的抽象，不是现成的 | ⚠️ 半个 |

**为什么后两条不成立**：周报不是"日报多一段"，它是**第二份产物** ——
而"产物"这个概念在平台里原本只有一份的假设：留痕不区分产物（看门狗会被骗）、
心跳只有一个 URL、调度里只登记了任务。**这三处才是真正的平台缺口**，
它们不在"区块注册表"这一层，而在"投递与监控"那一层。

**这条经验修正了本文 §六 的排序**：第 4 步（通道注册表）与"看门狗参数化成
任务描述符"（§4.4 第 6 条）的优先级被低估了 —— 它们才是"加第二份产物"时
真正挡路的东西。它已经作为**已知缺口**记在 CHANGELOG 里（周报没有看门狗）。

## 七、明确不做（防以后重复讨论）

| 不做 | 为什么 |
|---|---|
| **动态加载**（`importlib` / `entry_points` / 扫描目录） | 一张静态 import 的表就够；动态加载会破坏"零第三方依赖"与自检的静态扫描，还引入"装没装、加载没加载"的新故障面 |
| **插件市场 / 第三方生态** | 只有一个使用者 |
| **事件总线 / 钩子系统** | `journal` 已经是事实上的事件日志；再加一层是同一个坑的第三次 |
| **热插拔 / 运行时重载** | 会牺牲"崩溃可见"（现在内核不抛异常、失败如实报错）。对一个必须自己发现故障的系统，这是亏本交易 |
| **第四位构建号** | 单人单机不需要。等真在第二台机器上跑、或要"热修已发布版本"时再引入 |
| **为平台化而重写现有模块** | v1 的教训：551 行的时段选择器被整体砍掉，自评"最重要的一次减法" |

## 八、代价（不美化）

- **多一层跳转**：读代码时要先看注册表再看实现。三处硬编码 if 链其实**很好读** —— 这是真实的损失。
- **自检要多两项**，而且新增功能必须记得登记（第 6 步就是为了让"忘了登记"响亮地失败）。
- **多一份要维护的文档**（`KERNEL-CONTRACT.md`）。本项目文档已经不少 —— 所以它必须**短**：
  只写"哪些文件是内核、内核不许 import 什么、Item 的字段含义"。
- **收益要等第二个功能才兑现**：第 2–4 步落地时，手上没有新功能，
  会觉得"这是为了优雅而优雅"。**建议与 P1 周报一起做** —— 用它当第一个真实的验证用例，
  而不是先改结构再找用处。
- **一批断言要从"断文案"改成"断协议"**：现在 `selftest.py:2643-2661` 断的是
  "✅ 今日完成 1 件"这类字面量 —— 文案一动就红（这是它的优点），
  但区块可插拔之后必须改成断"区块声明的字段齐全、顺序正确"。
  **改断言本身就是这次改造的主要工作量之一**，不是附带。
