# 架构 v4：Telegram 单一入口 + Apple 应用为状态源

> 定稿于 **2026-10-03**。这份文档取代 v1（备忘录输入 + 顺延那套，见
> `archive/ARCHITECTURE-v1-notes-carousel.md`）。
>
> v1 的失败原因见文末「为什么推翻 v1」——**值得先读**，
> 因为 v4 的每一条约束都对应 v1 踩过的一个坑。

---

## 一、唯一约束

> **每个事实只有一个写入者。Apple 应用是状态源；agent 只「增」，
> 从不以自己为准去改或删。**

这一条推演出本文其余全部内容。设计上犹豫时，回到这句话。

---

## 二、核心设计：agent 无状态，journal 是传感器

这是 v4 相对 v1 的**根本修正**。

```
        ┌──────────────────┐
        │  Apple 备忘录     │ ← 状态源（唯一真相）
        └────────┬─────────┘
                 │ 只读 · 快照（电压表并联在此）
                 ▼
            journal（读数记录）

   agent ──追加写(单向)──→ Apple 备忘录
     ↑                          │
     └──────── 不回读 ───────────┘
          （不构成闭环 → 不会「左脚踩右脚」）
```

| | 电压表 | journal |
|---|---|---|
| 角色 | **传感器**，不是电源 | 观察记录，不是状态源 |
| 接法 | **并联**，不影响主回路 | **只读**，不参与写入路径 |
| 测什么 | 主回路真实电压 | Apple 应用的**真实状态** |
| 自带状态 | 无 | **无** |

**agent 没有「我的副本」这个东西**，所以不可能和状态源不一致。

### 为什么不做镜像副本

曾考虑让 `data/notes/` 保存备忘的**镜像**。它有两个必然缺陷：

1. **删了又被加回来**：你在备忘录里删掉一条，镜像不知道；若 agent 用镜像
   "重建"备忘录，会把你删掉的又造出来。
2. **删了却还被提醒**：镜像里那条还在，日报会提醒你一件早已处理完的事。

根因：**镜像是「第二份状态」，两份状态一旦不同，就得靠猜谁对** ——
又回到"猜身份"的老坑。

正解：**状态源只有一份（Apple 应用）**。agent 只在 journal 里记
「我提交过什么」和「我观察到什么」，而「谁还在」永远从 Apple 应用现读。

## 三、权限矩阵

| 存储 | agent 权限 | 你的权限 |
|---|---|---|
| **提醒事项** | 读（日报）+ **增** | 打钩（改状态）、改字、**删** |
| **Apple 日历** | 读（日报）+ **增** | 改时间、**删** |
| **Apple 备忘录** | 读**快照**（仅用于提醒）+ **增** | 改、**删** |
| **journal** | 增（追加，永不修改） | 读 |
| 项目目录 | 增、改 | 增、改、删 |

**「删除」这个动作全部在你手里。** agent 从不删任何东西 —— 这消除
"agent 误删 / 复活你删掉的东西"整类问题。

> ### 已撤销（2026-10-03）：曾经为「改分类」开过口子，现已收回
>
> **当时为什么开**：第一次真实使用时，一段感慨被判成待办；接着说「改为备忘录」，
> 而系统把它当成了**新内容** —— 纠正通道根本不存在。改分类必然要把原条目从
> 旧 App 移走，而上面那条约束禁止删除，于是开了个受控口子
> （只用明确 id 删、只有 `reclassify` 调用、每次记 journal）。
>
> **为什么撤销**：那个口子**从未在代码里实现过**。而且它要解决的问题，
> 现在有更干净的解法 —— 见 [`SYMBOL-SCHEME.md`](SYMBOL-SCHEME.md)：
> 类型由你**声明**（行首符号），Telegram 入口**不再承担任何"改"的操作**。
> 纠正的办法变成"带符号重发一条，旧的那条你在 App 里删"——
> **删除仍然只在你手里**。
>
> 于是「agent 从不删任何东西」这条约束**恢复为无例外**。
>
> | | 当时 | 现在 |
> |---|---|---|
> | 改分类怎么做 | 开个口子让 agent 删 | 你带符号重发 + 你在 App 里删旧的 |
> | agent 能删吗 | 例外允许（未实现）| **不能，零例外** |
> | 自检 | — | 逐模块断言写入端不含 `delete`（见 `selftest.py`）|
>
> 这次修订写在此处而不是悄悄删掉，因为**约束的价值在于被遵守**：
> 开过口子就要记下"开过又收回"，以及收回的理由 ——
> 而不是让文档和代码各说各话。

## 四、journal 的两条铁律

| 机制 | 内容 | 绝不包含 |
|---|---|---|
| **动作日志** | "我提交过什么"（id、正文、时间、结果） | 状态的权威判断 |
| **观察日志** | "我读到过什么"（快照摘要与差集） | 用于决定下次怎么写 |

### 写入路径（单向，不回读）

```
你说「备忘：荷载按名称命名」
   → agent 生成 id
   → **追加**到 Apple 备忘录
   → journal 记 {"event":"memo_added", id, text, at}
   → 完（不读回做判断）
```

### 感知路径（只读快照，产生差集记录）

```
21:30 日报前
   → **只读** Apple 备忘录快照
   → 与 journal 里「我写过什么」做差集：
       还在   → 仍未处理 → 到阈值就提醒
       不在   → 你已删除 → 记 memo_cleared，**永不再提醒**
```

**完整追踪**：删掉的东西在 journal 里也留了痕迹
（`memo_added` → `memo_cleared`），既不影响你，将来复盘还能看出
"这条提过、当天就处理了"。

## 五、冲突规则

**根本不存在冲突** —— 只有一份状态，agent 又没有副本。

| 你做的事 | agent 需要知道吗 | 结果 |
|---|---|---|
| 提醒事项里打钩 | ✅ 日报时读 | 计入完成 |
| 提醒事项里删掉一条 | ❌ 不需要 | 它不在列表里了，天然不出现 |
| 日历改时间 / 删除 | ✅ 日报时读 | 以日历为准 |
| **备忘录里删掉一条** | ✅ 快照时发现 | 停止提醒，记 `memo_cleared` |

**agent 不维护"我做过什么"的记忆用于决策**，每次都从 Apple 应用现读真相。

## 六、数据流

> **注意措辞**：Telegram 入口**不做语义理解**。你发的消息里带**行首符号**
> 声明类型（`#` 备忘、`@` 日历、裸输入或 `- [ ]` 待办），
> 系统只做「认符号 → 剥符号 → 写对应 App」。
> 详见 [`SYMBOL-SCHEME.md`](SYMBOL-SCHEME.md)。本文说"声明"，不说"解析"。

```
你 → Telegram 发一条（带行首符号）
        │
        ▼
   agent 收件守护进程：认符号 → 剥符号 → 分发
        ├─ 待办（裸输入 / - [ ]）──→ 提醒事项      「已记下（待办）：交电费」
        ├─ 日程（@…）──────────→ Apple 日历       「已记下（日程）：周五 14:00 项目周会」
        └─ 备忘（#…）──────────→ 追加写备忘录      「已记下（备忘）」
        │
        └─ 原始输入 + 落点 ──→ journal（追加，永不修改）
                    │
                    ▼
   你随时操作（唯一状态变更处）：
     提醒事项打钩 / 日历改时间 / 备忘录删条目
                    │
                    ▼
   21:30  agent **只读**三处快照 → 日报 → Telegram（+ Bark 冗余）
```

## 七、四个概念

| 概念 | 判据 | 状态源 | 完成态 |
|---|---|---|---|
| **待办** | 一件"要做的动作" | 提醒事项 | ✅ 打钩 |
| **日程** | "某时间点发生的事" | 日历 | ❌ 过去即结束 |
| **备忘** | 一条"记下来别忘了" | 备忘录 | ❌ 你删掉即结束 |
| **用户日志** | 观察到的读数 | journal | — |

### 待办 vs 日程

- 待办：`交电费` —— 有"做完/没做完"，可以没有时间点
- 日程：`周五 14:00 项目周会` —— 有时间点，不需要"完成"

**周期性事务**（每周一交周报）适合**日历** —— 它有 `recurrence`（重复规则），
而提醒事项的脚本接口不支持（实测其字典里无 repeat）。

## 八、日报

```
📋 2026-10-03 复盘
✅ 今日完成 2 件：勘察表盖章、交电费
⏳ 未完成 3 件：跟进竣工报验、…
📅 明日日程 2 项：项目周会 14:00、…
📝 备忘已放置 3 天以上：荷载要按名称命名
```

最后一行是**防遗忘机制**：只读快照里仍在、且 `memo_added` 超过阈值的条目
（默认 **3 天**，可调）。

### 时间表

| 任务 | 时间 | 作用 |
|---|---|---|
| **收件守护** | 常驻（`KeepAlive`） | 你发即处理 |
| **日报** | 每天 21:30 | 汇总 + 提醒 |
| **周报** | 周日 20:00 | 暂缓，等一两周数据后再说 |

## 十、失败与纠偏

| 情况 | 处理 | 后果 |
|---|---|---|
| Telegram 不可用 | **你直接在三个 App 里手动记** | agent 无需知晓，下周期读真相 |
| agent 解析错 | 你在对应 App 里改掉 | 同上 |
| 守护进程挂了 | 你手动记；恢复后无状态依赖 | 只损失"一次自动整理" |
| 任何不一致 | **以 Apple 应用为准** | agent 无副本，不会"坚持己见" |

**核心性质：agent 不维护"我做过什么"的记忆用于决策**，每次都从 Apple
应用读当前真相。所以任何环节挂掉都只损失一次自动整理，**不会造成数据不一致**。

## 十一、防掉坑判据

加任何新功能前，逐条检查。任一条命中，就说明又在造"有状态对话"：

```
✗ 需要跨两次交互记住东西（除了"这条的 id"）
✗ 需要重绘整条消息来体现进度
✗ 需要超时 / 重入 / 确认屏来处理"用户没按预期操作"
✗ 需要猜"这条是不是同一件事"
✗ 让 agent 拥有"删"权限
✗ agent 用自己写的东西作为下次写入的依据
✗ agent 在"要动你的数据"时不先回显确认
```

**「猜身份」的替代方案**：不要猜，要找**天然的精确指代**。

> ### 已裁决（2026-10-03）：两条候选，都判定为"不做"
>
> 下面这两条都曾是"天然精确指代"的候选，逐条用上面的判据筛过，结论是不做 ——
> 记在这里，免得以后再讨论一遍。
>
> | 候选 | 机制 | 为什么不做 |
> |---|---|---|
> | **原生回复作引用**（回复回执来补全） | `reply_to_message` 免费携带 `message_id` 与 `text`，零猜测 | 命中判据 1、3：要记住"那条回执对应哪条待补全的事"，等于重建 pending 状态 —— 而 pending 正是 2026-10-03 两次故障的所在地 |
> | **按钮追问 / 表单化**（v1 时段选择器的形态） | 你点选，机器判断 | 命中判据 1、2、3；v1 已用 **551 行选择器**付过学费，并自评"本项目最重要的一次减法" |
>
> **替代做法**：类型由你**声明**（行首符号），缺什么就**带符号重说一条完整的**。
> 代价是几秒钟重打字；收益是 Telegram 层不需要任何跨消息状态。
> 详见 [`SYMBOL-SCHEME.md`](SYMBOL-SCHEME.md) 与
> [`TELEGRAM-DESIGN.md`](TELEGRAM-DESIGN.md) §5.3。

**对照 v1 的失败**：

| v1 的功能 | 命中的判据 | 结果 |
|---|---|---|
| 时段按钮选择器 | 1、2、4 | 551 行，最后被砍 |
| 完成按钮 | 2 | offset 丢点击 bug |
| 顺延的防链式判据 | 6 | **把没做完的事静默拦住** |
| 备忘镜像副本 | 6 | 复活你删掉的条目 |

## 十二、取舍

| 得到 | 失去 |
|---|---|
| 每事实单一写入者 → **不可能两处不一致** | 备忘录输入（更顺手，但可离线手写） |

| 类型判断 100% 归你 → 判错不再静默 | 忘了打符号 → 按默认落点（**看得见**，可去 App 改）|

## 附：为什么推翻 v1

v1（备忘录当天页 + 标记解析 + 顺延 + 提醒事项打钩）实际运行了两天，
暴露出**同一个架构缺陷的四次不同表现**：

| 事实 | 存在几处 |
|---|---|
| 一条待办的状态 | 备忘录 `[ ]` + 提醒事项 `completed` + 留档 JSON = **三处** |

为弥合这三处，v1 堆了约 **280 行补丁**（`completion.py` 129 行合并三处状态、
`reconcile.py` 153 行专门把一处改成另一处），以及遍布 6 个文件、9 处调用的
`content_fingerprint`（"猜这两条是不是同一个东西"）。

而"猜身份"引发了四次同源错误：

| 拿什么当身份 | 后果 |
|---|---|
| 行号 | 编辑后行号位移 → 时段错配 |
| 原样文字 | 顺延后文字变形 → 重复建条目 |
| "跨天同一条" | 新一天继承旧的完成状态 → 没得打钩 |
| 来源条目的 `⟳` 标记 | **把没做完的事静默拦住** |

**四次都是同一个错误的变体：拿不合适的东西当身份。**

v4 的解法不是"把身份猜得更准"，而是**让这个问题不存在** ——
状态只有一处，就不需要判断"这两条是不是同一个"。

### v1 与 v4 的对照

| | v1 | v4 |
|---|---|---|
| 输入 | 备忘录当天页（+ Telegram） | **只有 Telegram** |
| 待办归属 | 提醒事项（但与备忘录双写） | 提醒事项（**唯一**） |
| 日程 | ❌ 未实现 | Apple 日历 |
