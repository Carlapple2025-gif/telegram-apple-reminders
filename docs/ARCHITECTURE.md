# 架构：五个组件的确切分工

这份文档记录 **2026-10-02** 定稿的架构。每个结论都来自实测，不是设想。

## 一句话

> 你用备忘录记录、在提醒事项里打钩；Mac mini 负责整理、同步、汇报；
> Telegram 是对话与归档的载体；Bark 是唯一用于强提醒的通道。

## 为什么是这五个组件（各自的不可替代性）

| 组件 | 角色 | 不可替代之处 | 实测依据 |
|---|---|---|---|
| **备忘录** | **记录**（你写） | 输入体验最好；是你的原始表达，机器不修改 | 一天一页 + 标记解析已跑通 |
| **提醒事项** | **执行 + 打钩** | `completed` **可读可写** —— 这是备忘录做不到的 | 见下方能力对比 |
| **Telegram** | **对话与归档** | 唯一能**双向**的通道：播报、周报归档、**回答提问** | `getMe`/`sendMessage`/`getUpdates` 均通，**直连无需代理** |
| **Bark** | **强提醒** | 唯一能穿透专注模式；直连无第三方依赖 | 已验证多次推送成功 |
| **Mac mini** | **常开执行** | 定时、调 API、读写三端 | launchd 任务已装且权限验证通过 |

## 关键洞察一：提醒事项补上了备忘录的硬伤

| 能力 | 备忘录 | 提醒事项 |
|---|---|---|
| 代码生成可点勾选框 | ❌ 写入时 `class`/`data` 被剥离 | ✅ 原生就是 |
| 代码读完成状态 | ❌ 读不到 | ✅ `completed` |
| 代码写完成状态 | ❌ 写不了 | ✅ `completed` |
| 到期时间 / 提醒 | ❌ 不存在 | ✅ `due date` / `remind me date` |
| 锁屏小组件打钩 | ❌ | ✅ |
| 到期通知 | ❌ | ✅ |

**备忘录用代码生成不了可交互勾选框，但提醒事项在 API 层面原生支持完成状态。**
所以「待办」交给提醒事项，不是妥协，而是更正确的分工。

## 关键洞察二：Telegram 让「agent 提问」真正可行

之前设计里有个一直没解决的矛盾：

- 原则是「判断权交给用户，agent 不猜」
- 但 agent 在**定时批处理**里运行，**没法提问**

于是「渐进式披露」（"这条放哪个时段？"）只能退化成"标记进留档，等你哪天看到"——
等于放弃了它。

Telegram 补上了这个：

```
21:30  agent → Telegram：「今天有 2 条没写时段：
                          1) 1215 305重新编号  2) 明天要交电费
                          回复如「1上午 2明天」」
你    → 直接回复
agent → getUpdates 读取 → 写入留档
```

**超时策略**：不回复则走默认（不指定时段），不阻塞其他流程。

## 关键洞察三：通道按特长分工，不让关键路径依赖单一通道

| 消息类型 | 通道 | 理由 |
|---|---|---|
| 需要立刻处理的 | **Bark** | 穿透专注模式；**直连**，不依赖任何第三方存活 |
| 日报 / 周报 / 归档 | **Telegram** | 可回看、可搜索、历史天然留存 |
| agent 的提问 | **Telegram** | 只能用它（Bark 是单向推送，回不了） |

**fail-safe**：Telegram 因网络不可用时，Bark 那条依然能把你叫起来。
这解决了早先「代理挂了 → 通知发不出 → 当天任务失败」的单点问题。

> 旧结论「`api.telegram.org` 在 Mac mini 上不可达（需代理）」**已被推翻**：
> 2026-10-02 实测直连返回 302，`getMe`/`sendMessage`/`getUpdates` 全部正常。
> 网络环境变了，结论要跟着变。

## 唯一的权威：完成状态以提醒事项为准

加入三个组件后，「完成」有了三个可能的表达处：

```
备忘录里的 [x]        ← 你手写打钩
提醒事项的 completed  ← 你在锁屏点
Telegram 里的回复      ← 你说"这条做完了"
```

**规则**：`completed`（提醒事项）是**唯一权威**。

| 你的动作 | agent 的处理 |
|---|---|
| 在提醒事项点勾 | 直接读 `completed`（权威） |
| 在备忘录写 `[x]` | 读取后**同步写入**提醒事项（等价表达） |
| 在 Telegram 说"完工" | 代你在提醒事项打钩 |

**冲突时倾向「完成」**：打钩过就算完成，不因另一处没钩而回退。

之所以这样定：**`completed` 是三者中唯一代码可读写的状态**。备忘录的勾选状态
根本不存储在 HTML 里（实测），Telegram 的回复是自由文本、不可靠。

## 数据流

```
早上 08:00  你在备忘录写今天的页
              （- [ ] 待办  * 备忘  @时段）
                    ↓ agent 解析
              agent 把「待办」同步到提醒事项（幂等，用 笔记id+行号 去重）
                    ↓
白天        你在锁屏小组件/提醒事项点勾  ← 唯一的完成状态来源
                    ↓
21:30       agent 读 completed → 写进留档 → Telegram 日报
              · 有疑问 → Telegram 提问，等你回复
              · Bark 只在需要立刻处理时用
                    ↓
次日 07:00  agent 把未完成的（completed=false）顺延到新一天的页
              + 在提醒事项里更新到期日
```

## 分阶段实现（已与用户确认顺序）

| 阶段 | 内容 | 状态 |
|---|---|---|
| 1 | **提醒事项联动** | 进行中：能力探测 → `reminders.py` → 同步 → 改顺延/日报 |
| 2 | **Telegram 日报/周报 + 提问** | 待做 |
| 3 | 智能体失败诊断（`dsh --profile headless`） | 待做 |

先做 1 的理由：它解决的是**核心体验**（打钩终于不用在备忘录里手动转格式），
而 Telegram 是体验增强。

## 未解决 / 待观察

| 项 | 说明 |
|---|---|
| 提醒事项里条目的生命周期 | 已完成的要不要自动清理？暂定：保留，交由你在 App 里处理 |
| 清单勾选框的显示 | 备忘录里仍是纯文本标记，需你手动转一次（仅为 App 内可点） |
| Telegram 提问的频率 | 需实际用起来才知道会不会烦。设计上"只在必要时问" |
| 周报形态 | 未设计。等日报跑一两周有数据后再定 |
