## 一、为什么要单独写这份

`TELEGRAM-DESIGN.md` 把交互模型定死了（符号声明、只报错不提问、删 pending 与按钮），
但**没有任何一份文档管过"措辞"**。于是这一层出现了三类问题：

1. **说的是旧规矩** —— 符号方案落地后，仍有文案在教"不打符号也能进日历/备忘录"；
2. **该响的没响、不该响的乱响** —— 回执和日报用同一个音量，且唯一的"弹窗"原语没有调用方；
3. **该有反应的地方完全没反应** —— 发语音、发图、回执发送失败，三种情况都是"静默"。

第 3 类与本项目反复强调的「宁可报错，不可静默」直接冲突，所以值得单独成文。

## 四、发现清单（V1–V9）

每条给：现象 / 证据 / 影响 / 可选项。**V1–V3 是"说的错、响的错、静默"，V7–V8 是收尾欠账。**

### V1｜启动通知教的是符号方案之前的用法 ★ 最该先改　→ **✅ 已改（选 A + 冷却）**

**现象**：三条样例里**两条是错的**。

| 启动通知说 | 实测（`routes.py --base 2026-10-04`） |
|---|---|
| `明天交电费` → 提醒事项 | ✅ `todo：交电费 @ 10月5日 周一` |
| `周五下午两点项目周会` → 日历 | ❌ `todo：项目周会`（进**提醒事项**，时间只进备注） |
| `想起一件事，…` → 备忘录 | ❌ `todo：想起一件事…`（进**提醒事项**） |

**证据**：三条全部实跑过，见 §附录C。两条错的原因是：符号方案要求 `@` / `#` 声明类型，
而这条文案写于符号方案之前，之后没人改。

**影响**：它是**聊天里唯一的说明书**（没有 `/help`，没有 `setMyCommands`，
符号表只活在文档里）。而日志显示 17.6 小时内进程启动 13 次、其中约 10 次真的发出了这条通知
（见 §附录D）——**一天被教错十次，且每次都教同一件错事。**

**可选项**

| | 做法 | 代价 |
|---|---|---|
| **A ✅ 采纳** | 改成真符号表（三条：裸输入→待办、`#`→备忘、`@`→日历） | 无，只是换文案 |
| B | 只报"已启动，发 `/help` 看用法" + `setMyCommands('/help')` | 多一次交互才能看到符号表 |
| C | A + B：通知里放极简版，`/help` 放完整版 | 两处文案要同步（新的一致性负担） |
| **D ✅ 部分采纳** | 静音 + 降频（冷却 300s → 3600s） | 重启不再"响"，但聊天里仍有记录可查 |

> 裁决（2026-10-04）：**只改启动通知**，不做 `/help`、不设 `setMyCommands` ——
> 所以"两份文案要同步"这个新负担没有引入。
> 防复发靠的是 `USAGE_EXAMPLES` + 自检里那条"把样例真的丢进 `route()`"的断言。

### V2｜回执和日报用同一个音量　→ **✅ 已改**

**现象**：记一条待办 → 手机"叮"；21:30 日报 → 手机也"叮"；守护重启 → 还是"叮"。
**你没法从声音判断哪条值得立刻看。**

**证据（行号是诊断当时的）**：`tg.send(reply)`（原 `daemon.py:194`，现 `daemon.py:305`）与
`notify.send_telegram`（[`notify.py:139`](../src/notify.py)）都不带音量参数；
`disable_notification` 参数已存在但零调用方。

**影响**：回执的横幅是**纯噪音**——你刚发完消息，人就在聊天界面上，
横幅不提供任何新信息，却会在锁屏/专注模式上抢一次注意力。

**✅ 裁决并实施**：回执 `silent=out.ok`、启动通知静音；**失败与日报保留横幅**。
Bark 那一侧早就有明确分工（强提醒），Telegram 侧这才跟上 ——
所以这一条不是"要不要吵"，是**把分工补齐**。

> 一个容易想错的点：`disable_notification` 的官方语义是
> "Users will receive a notification with no sound" —— **不响不震，横幅与未读角标仍在**。
> 所以"静音"不等于"看不到"，这个选择没有盲区。

### V3｜写入成功但回执发不出去 → 你什么都看不到 ★ 唯一的"静默写入"　→ **✅ 已改（选 A + C）**

**现象**：Telegram 抖动时（17.6 小时内 176 次拉取失败，见 §附录D），
条目**已经写进 App**，但你收不到任何回执 —— 连"没记成"也没有。

**证据（行号是诊断当时的）**：`handle_message` 里的 `tg.send(reply)` **没有 try**
（原 `daemon.py:194`）；异常冒到 `run_once` 的兜底（原 `daemon.py:247`），
兜底里**再发**一条"❌ 这条没处理成"——网络还是坏的，于是也失败，被 `except: pass` 吞掉。

**影响**：这与「宁可报错，不可静默」冲突，而且是最坏的一种静默：
**静默地成功了**。你的自然反应是"没记上，重发一遍" → 重复条目。
（现有缓解：21:30 日报读的是 App 真状态，所以最迟当晚它会自己冒出来。）

**可选项**

| | 做法 | 代价 |
|---|---|---|
| **A ✅ 采纳** | 回执失败重试 2 次（5s / 15s） | 抖动时能救回大部分；仍会漏 |
| B | 回执失败落盘到 `daemon-state.json`，下一轮补发 | 多一类状态（但属通道机制，与 offset 同类）——**未采纳** |
| **C ✅ 部分采纳** | 最终失败记进 journal 的 `error` 读数 | 只有排查价值，你当场仍不知道 |
| D | 什么都不做，只在 USER-GUIDE 写明"没回执 ≠ 没记上，去 App 看一眼" | 零成本，但把负担给了你 |

> 裁决（2026-10-04）：**A + C**。
> **不做 B 的理由是历史**："落盘 + 下轮补发"必然带 TTL，
> 而"带 TTL 的待发槽位"正是 2026-10-03 那两次真实故障的所在地（见 SYMBOL-SCHEME §4.6）。
> 重试覆盖瞬时抖动，journal 留审计，最迟当晚日报兜底 —— 够了。
>
> 两个实现约束：**重试必须放在调用方**（daemon），不能塞进 `telegram.send` ——
> 通道层那条注释写明了"静默重试会让'没发出去'变成'以为发出去了'"；
> **非通道类异常不重试**（编程错误不该被说成网络抖动）。

### V4｜非文本消息静默丢弃　→ **✅ 已改（选 A + B）**

**现象**：发语音、图片、文件、贴纸 → **完全没有反应**，日志也没一行。
**证据**：`text = (msg.get("text") or "").strip()` → `if not text: continue`
（原 `daemon.py:244`，现 `daemon.py:356`）。
**影响**：对一个"记录"入口，发张图或说一段话是很自然的动作；现在的表现等于"它死了"。
**✅ 裁决并实施**：回一句陈述（`NON_TEXT_REPLY`）+ 记一行日志；**服务类消息仍然安静跳过** ——
"不是文字"和"不是内容"要分开，后者回一句是打扰。
（已知取舍：相册会连发几条，于是会收到几条同样的回执。没做节流 ——
没有业务状态可依据，且这是罕见路径。）

### V5｜日报页脚在暗示一个不存在的能力　→ **✅ 已改（选 B）**

**现象**：`做完的在「提醒事项」里打钩 ✓` 紧接着 `（发一句给我也行，比如「明天交电费」）`
—— 读起来像"发一句就能打钩"。

**证据**：[`report.py:214`](../src/report.py)。机器人**没有**打钩能力：
`completion.py` 属 v1 路径（`sync.py` / `push_tasks.py` 用），`daemon.py` 只写不读，
所以发「明天交电费」只会**新建一条**。

**影响**：误解的代价是重复条目 + 你以为完成了。
**✅ 裁决并实施**：改成 `想加一条就直接发：交电费 · # 想法 · @周五两点 周会` ——
只说自己真能做的事，顺带把符号表每天念一遍（`SYMBOL-SCHEME.md §6` 说好的缓解措施之一）。

### V6｜回执在复述原文；待办的时间在回执里丢了　→ **✅ 已改（选 A + B）**

**现象**：`✅ 已记下（备忘）：<你的原文>` —— 100 字的感慨会被原样回声一遍；
而**待办**给了时间却看不到：发 `明天交电费` → 回执只有 `✅ 已记下（待办）：交电费`，
"明天"去哪了要靠打开提醒事项看备注。日程则会显示 `10月9日 周五 14:00`——**同一件事两种待遇**。

**证据**：`_reply_ok` 里只有 `Kind.EVENT` 分支追加时间明细
（原 `intake.py:132`，现 [`intake.py:147`](../src/intake.py)）+ 实测。
**✅ 裁决并实施**：待办也显示时间 + 超长正文截断（20 字 + `…`）。
- 待办那行**必须**注明"只写进备注，不会到期提醒" —— 否则 `10月5日 周一`
  看起来像会到期通知，而提醒事项**刻意不设到期日**（见 `intake._real_add_todo`）。
- 为此给 `whens.format_when()` 加了 `all_day_note` 开关：**时间格式仍只有一处实现**
  （在 intake 里再抄一份格式化就是"同一件事两处实现"的开端）。
- 复述原文被砍掉不影响安全网：去向那半句（`→ 在「备忘录」里`）才是"符号打错能立刻看见"的载体。

> 顺带：`TELEGRAM-DESIGN.md §5.1` 的倾向原本是"发，但**极简一行**"，
> 实现出来是 3 行 + 全角缩进 + 复述原文。**倾向与实现从没对齐过**，这条该一起定。

"先回执再干活"需要多发一条消息。
**可选项**：A) `sendChatAction("typing")`（**不加消息条数**，但只持续 5 秒）／
B) 先发"收到"再补结果（+1 条消息，与 V2 的静音联动）／C) 不动。
**注意**：日志显示"没反应"的主因是**网络抖动**，不是 25 秒轮询设计——
所以 `§5.6` 的结论（缩短轮询）不必再议，问题在别处。

## 五、文案层的正面结论（别一起改掉）

- 4 条报错都是**陈述事实 + 给出路**，符合「只报错不提问」的裁决；
  唯一像"要求"的 `请带时间重发一条` 不引入任何状态，合规。
- `(这个时间今天已经过了，我放到了明天 —— 要改就去日历里改)`：既说明机器做了什么，
  又给出纠错路径，**是本项目文案的范本**。
- 日报里 `（提醒事项里还没有条目 —— 发一句给我就行）` 区分了"读不到"与"没有"，同样是范本。
- `PDCA_SUPPRESS_SEND` 这个**测试期静音阀**（[`notify.py:153`](../src/notify.py)）
  已经证明了"音量"是可以被显式管理的——V2 想做的正是同一件事，只是面向你而不是面向测试。
