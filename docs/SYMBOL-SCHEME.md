## 一、要解决的问题

Telegram 入口上线后，**类型判断**这件事被交给了代码里的词表去猜。实测一天 4 次真实交互，
3 次出问题，其中 2 次是同一个根因。

| 交互 | 你发的 | 系统做的 | 问题 |
|---|---|---|---|
| 1 | 一段关于"学原理"的感慨 | 判成**待办** | 陈述句感慨被"动词打头 + 短句"判据吃进去 |
| 2 | `改为备忘录` | 新建一条叫「改为备忘录」的**备忘** | 把"操作"当成"内容" |
| 3 | `上午九点`（回答追问） | 新建一条标题是「上午九点」的**日程** | 把"补全"当成"新内容" |

**根因不是判据不够准，是"让机器猜意图"这个决定本身。**
每修一个 case 就加一个词/调一个窗口 → 过拟合点只增不减 → 错误不可收敛。

## 二、方案：类型由你声明，不由机器推断

```
- [ ] 交电费                  → 待办（提醒事项）
（裸输入）交电费               → 待办（提醒事项）   ← 最高频，零符号
# 学原理比学语法重要           → 备忘（备忘录）
@周五下午两点 项目周会         → 日历
```

**一句话：认出行首符号 → 剥掉符号 → 按符号写对应 App。系统不理解任何东西。**

### 2.1 符号表（最终）

| 类型 | 写法 | 必填？ |
|---|---|---|
| **待办** | **不打符号**（裸输入），或 `- [ ] 交电费` | 不用打 |
| **备忘** | `# 内容` | 要打 |
| **日历** | `@周五下午两点 项目周会` | 要打 |
| 元信息 | **取消这个概念** | — |

> **2026-10-04 追加第四种声明：`/命令`（只读查询）。**
> 目前只有一条：`/list`（= `/ls` `/today` `/列表`）—— 看未完成的待办 + 今天/明天的日程。
> 它与上面三条的区别是**哪个 App 都不写**，所以判定与实现都不在 `routes.py` /
> `intake.py`，而在 [`commands.py`](../src/commands.py)（守护在通道层按字面 `/` 分流）。
> 判据仍然是**行首字符**，所以 `list` 不带斜杠就是一条待办 —— 与"类型由你声明"同源。

**字符容忍**（v1 已实测，照单全收，不重新发明）：

```
待办   - [ ]    - [x]    - [X]    - [✓]    - [✔]      全/半角复选框都认
       破折号归一化： - – — − ‐
备忘   #        *  •  ·  ・                          项目符号归一化
日历   @        ＠                                    全角也认
```

### 2.2 两处必须补的剥除（现在缺）

| 符号 | 现状 | 要做的 |
|---|---|---|
| `#` 行首 | ❌ **原样进正文** | 补剥除 |
| `@` 非时段 | ❌ **原样进正文** | 补剥除，并取消 `@时段` 的旧剥离 |

不补的话，你会在提醒事项/日历里看到 `# 学原理…` 这种带符号的正文。

### 2.3 两处冲突的处置（已确认）

| 冲突 | v1 的语义 | 本方案 | 理由 |
|---|---|---|---|
| `#` | 元信息（跳过该行） | **备忘** | v4 的日期由守护掌握，不需要你在正文里写日期 |
| `@` | 时段（`@中午 勘察表盖章`） | **日历** | 时段功能 v1 已整体砍掉（551 行选择器） |

两处都不是"抢"，是**确认它们已经没人用**。但必须写进文档，否则以后读到 v1 会打架。

### 2.4 符号为什么选这三个

| 位置 | iPhone 键盘 | 候选 | 结论 |
|---|---|---|---|
| 字母层 | 最省事 | `!` `?` | `!` 与自然语言句首感叹号冲突 |
| 数字层 | 一下 | `#` `/` `-` | ✅ **`#`** |
| 符号层 | 两下 | `@` `*` `&` | ✅ **`@`**（`*` 已被 v1 用作备忘）|

`#` / `@` 的关键优势：**`parse.py` 里已经实现并实测过输入法差异**。
换符号要重测一轮智能标点，成本不划算 —— 除非你觉得别扭。
（用户已明确：若会造成误解可以换。目前评估是"不误解，只是与 v1 旧义撞"。）

## 三、为什么这样更可靠

| | 现在（词表猜） | 符号声明 |
|---|---|---|
| 判据在哪 | 代码里，约 700 字词表 | **你的输入里** |
| 出错形态 | 判错 → 写错 App（**静默**） | 忘打符号 → 按默认落点（**看得见**） |
| 可测性 | 只能测"猜得准不准" | **完全确定性**，可离线回归 |
| 错误收敛性 | ❌ 加词 → 过拟合点只增不减 | ✅ 没有"词表"这个东西可加 |
| 代码量 | 364 行 | 约 60 行 |

### 4.4 一个顺带修掉的真问题

`daemon.py:312` 现在写的是「按用户指定的类型分派（**跳过分类**）」，实际实现是：

```python
c = classify.classify(text) or classify.Classified(kind, ...)
c.kind = kind          # ← 猜完再覆盖回你选的
```

先拿分类器结果（为了蹭里面的时间解析），再覆盖类型。"跳过分类"这句话是假的 ——
这就是"两套判断逻辑打架"的具体形态。删掉 `classify` 后它自然消失。

### 4.5 时间解析归谁（**必须明确，否则会变成新补丁**）

`@周五下午两点 项目周会` 里，"周五下午两点"必须被解析出来 ——
**这是时间字面量解析，不是猜语义**，所以它不能跟着 `classify.py` 一起删。

**唯一入口：`whens.parse_when()`。** 分工如下：

| 步骤 | 谁做 | 说明 |
|---|---|---|
| 1. 认出行首符号 | `parse.py` | `#` / `@` / `- [ ]` / 裸输入 |
| 2. 剥掉符号 | `parse.py` | 得到正文（如 `周五下午两点 项目周会`）|
| 3. 解析时间 | **`whens.parse_when()`** | 返回 `When`（start/end/has_date/has_time/…）|
| 4. 解析重复规则 | **`whens.parse_recurrence()`** | 从 `classify.py` 搬来（`@每周一 交周报`）|
| 5. 去掉时间短语得到标题 | `whens` | 现在叫 `_strip_time_phrases`，在 `classify.py` 里，**要搬过来** |
| 6. 写日历 | `applecal.add()` | 时间语义已由 Python 算成整数，AppleScript 只赋值 |

> ⚠️ **第 5 步是最容易被漏掉的一步**。它现在藏在 `classify.py` 里，
> 而 `classify.py` 的删除清单里包含 `_strip_time_phrases`（15 行）。
> 若只是"删掉 classify"，标题就会变成 `周五下午两点 项目周会`（时间词混在标题里）——
> **这就是一个典型的补丁起点**。所以搬迁时这 15 行要一起搬到 `whens.py`。

**判断标准**：凡是"从字符串里认出时间/日期/重复规则"的，都归 `whens.py`；
凡是"猜这条属于哪个 App"的，全部删掉 —— 那是符号的职责。

### 4.6 `pending` 与按钮：全部删除（已裁决）

原表里写的"按钮相关逻辑随 §5 定论处置"是**悬空引用**（那一节没有讲按钮）。
现按 2026-10-03 的裁决直接定死：

| 要删的 | 位置 | 理由 |
|---|---|---|
| `_ask_keyboard()` | `daemon.py` | 不再"选一个" |
| `_handle_callback()` + `_CB_CARRY` | `daemon.py` | 不再有按钮回调 |
| `save_pending` / `load_pending` / `clear_pending` / `_pending_file` / `_pending_record` / `PENDING_TTL_HOURS` | `daemon.py` | 不再需要跨消息状态 |
| `answer_callback` / `wait_for_callback` / `drain_stale_callbacks` / `edit_with_buttons` | `telegram.py` | 调用方消失后一并清掉（`edit_with_buttons` 可留，日报若需重绘才用）|

**依据**：`ARCHITECTURE.md` §十一 判据 1「✗ 需要跨两次交互记住东西」——
按钮追问正是命中这一条的那个形态。2026-10-03 的两次故障
（槽位被清、按钮绑错消息号）都发生在这套机制里。

**这一条同时消掉了 `TELEGRAM-DESIGN.md` 里 `callback_data` 与 `pending` 两类状态** ——

## 六、残留风险（不美化）

| 风险 | 说明 | 缓解 |
|---|---|---|
| **忘打符号 → 进待办** | 这是"裸输入默认待办"的必然代价。今天那条感慨就是这种情况 | 回执如实显示去向（**回执见 TELEGRAM-DESIGN §5.1，倾向发**）；日报每天念一遍 |
| `@` 后仍要解析时间 | `@周五` 的"周五"要靠 `whens.py`，所以它不能简化掉（分工见 §4.5）| 保留 `whens.py` 全部时间词汇 |
| **`@` 后写了没法解析的时间** | 例如 `@下辈子 交电费` | **只报错、不写入**（§5.3），不退回备忘、不猜 |
| 改类型要去 App | 这是"不做修改操作"的代价 | 也是它的收益：零误改风险（`reclassify` 已撤销，见 ARCHITECTURE §三）|
| 符号要重新适应 | 你原来的 `-` = 待办习惯，要改成"裸输入就是不打招呼的待办" | `- [ ]` 仍可用，习惯不用全改 |
| 自检项目数会下降 | 现在 526 项里有一大批在测"分类猜得准不准" | 不是退步：判据少了，测试也该少。提交时写清减了哪些 |

### 5.3 `@` 后时间解析不出来 → 只报错，不写入

```
你发：  @下辈子 交电费

系统回：❌ 没记成：这条日程的时间我认不出来
        　　（我认得的时间写法：周五 / 明天下午两点 / 10月5日 …）
        　　请带时间重发一条，或改用 # 记成备忘
```

**不做的三件事**（都是曾经的候选，逐条否决）：

| 候选 | 为什么不做 |
|---|---|
| 退回当备忘写入 | **猜**。你说 `@` 就是要进日历，退成备忘等于替你改主意 |
| 追问"什么时候？" | 命中判据 1、3（跨两次交互 + 超时重入），就是被砍掉的 v1 选择器形态 |
| 用默认时间（如今天 9:00）| 最坏的一种：**静默写入一条错时间的日程** |

**这条与「宁可报错，不可静默」是同一条原则**：报错是陈述事实，提问是要求你再交互一次。
前者不引入状态，后者引入 —— 所以只做前者。
